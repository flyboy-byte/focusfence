# Repository-by-Repository Relevance

- **DistillNET (C#, MPL‑2.0)** – An Adblock-Plus–style filtering library.  CloudVeil’s fork of **DistillNET** (from *TechnikEmpire*) is a high‑performance engine for matching HTTP requests and HTML content against large ABP-format lists.  It prioritizes raw speed (parse and lookup benchmarks are in the README) at the cost of data duplication.  *Relevance:* Offers a proven model for fast, large-rule filtering and list management (domains, URLs, ABP rules).  However, it’s C#/.NET, heavy on RAM/disk, and licensed MPL-2.0, so direct reuse in Android/Kotlin is unlikely.  It is valuable mostly as a conceptual reference for a local filtering engine (e.g. domain-indexing, cache strategies) rather than code to copy.  

- **Filter‑Windows (C#, MPL‑2.0)** – The core CloudVeil Windows content filter suite.  This is a large multi-part project (service, GUI, kernel hooks, Warden UI, installer, etc.) providing transparent HTTP/S filtering on Windows.  It includes Windows-specific modules (e.g. *FilterAgent*, *WinDivert* integration, *Sentinel*/“Warden” UI for reports, anti-uninstall *InstallGuard*, etc.) and a shared “CloudVeil.Core” library.  *Relevance:* Demonstrates how CloudVeil divides filtering into **kernel/network hooks** (to divert traffic) vs **policy engine** vs **UI/management**.  It shows cross-platform layering: common filter engine code plus Windows adapters.  However, the Windows code (C#/.NET, WinDivert) is mostly irrelevant to Android; focus should be on the architectural separation (e.g. *Filter.Core* vs *Platform* adapters) rather than on any code.  It does *not* align with FocusFence’s mobile/local philosophy (it assumes admin control and heavy infrastructure), but it does contain filtering engine concepts (though using GPL/MPL components under Windows).

- **FilterManager (PHP, MPL‑2.0)** – A web-based management console (Laravel/PHP) for CloudVeil Windows filters.  It lets an administrator upload policies, categorize content, and view reports.  Notably, it supports uploading *Apache OpenNLP* document-classification models and assigning categories to groups.  *Relevance:* Illustrates CloudVeil’s policy model: categories, groups, exceptions, and even ML model imports.  The actual UI code is out-of-scope (it’s remote/admin focused), but it shows how policies can be configured and structured.  FocusFence should **not** become a remote-managed system, but understanding this policy/data model can inspire a **local** policy structure (e.g. rule groups or category tags).  The OpenNLP integration (for document categorization) is interesting but likely too heavy for a local Android app.  This repo is mostly a “study” reference, not reuse, and much of it conflicts with the local-first/owner-control philosophy.

- **filterproviderlib‑apple (Swift, MIT)** – A Swift library “implementation of CV4W filtering engine.” There is no README text beyond “FilterProviderLib” and MIT license, but its existence tells us CloudVeil built a reusable filtering library for iOS.  *Relevance:* Conceptual only – it shows CloudVeil aimed for a modular engine that can be embedded (in iOS’s Content Filter framework, presumably).  We cannot reuse Swift code, but this affirms the value of a platform‑independent engine core.  It also is MIT-licensed, so if someone rewrote FocusFence in Swift, some code might be ported.  For our Android focus, we note that a similar standalone “engine library” approach is viable.

- **CitadelCore (C#, MPL‑2.0)** – A cross-platform HTTP/S (and WebSocket) proxy/filter library.  It is an *abstract* filtering proxy (derived from TechnikEmpire/CitadelCore) that bundles a full HTTP/S server and exposes callbacks at various stages for filtering, without providing the OS-level hooking.  *Relevance:* Conceptual: shows a “generic proxy engine” design where content inspection hooks are separate from traffic diversion.  CloudVeil intended platforms to supply a mechanism (VPN, WinDivert, etc.) to route traffic into this core.  For FocusFence, this model is instructive in principle (engine vs. platform integration), but CitadelCore itself is C#/.NET and not directly portable.  It is MPL-2 licensed.  It underscores the idea that protocol parsing and policy should be decoupled from how traffic is captured, which aligns with focusing on DNS/HTTP filtering without committing to a specific diversion method.

- **FilterCore (C#, MPL‑2.0)** – Essentially the same idea as CitadelCore, another fork of TechnikEmpire/CitadelCore.  *Relevance:* Same as above – not unique to Android, but reinforces the pattern of an engine+adapter.  (These likely share code.)

- **gotun2socks_orig (Go, BSD‑2-Clause)** – A Go implementation of *tun2socks*, used in CloudVeil’s Android VPN stack.  It’s a fork of yinghuocho/gotun2socks.  *Relevance:* Highly relevant for VPN-level work.  If FocusFence ever routes more than DNS (e.g. all traffic via VPN), `tun2socks` is a known solution to send device traffic into a user‑space proxy.  BSD-2-Clause license means reuse is legally fine.  However, an Android app would likely use a built-in library or JNI for this, not this Go code.  Still, the concept of TUN→socks is worth noting.  

- **goproxy / goproxy-managed (Go, BSD/MIT)** – `goproxy` is a Go HTTP proxy library (CloudVeil fork of elazarl/goproxy); `goproxy-managed` is a .NET wrapper for it.  *Relevance:* These are components of CloudVeil’s network layer (likely used in their proxies or services).  For FocusFence, we can note that goproxy (BSD-3) is a known proxy library.  In principle, FocusFence’s VPN could point to a proxy; however, we wouldn’t use Go libraries in Android, so this is only indirectly useful.  No direct reuse in Android, but they confirm CloudVeil uses established HTTP proxy libraries rather than homegrown ones.

- **dotnet-icap-server (C#, MIT)** – A small ICAP server implementation.  *Relevance:* This was meant to let CloudVeil talk to content filters (like e2guardian) via ICAP.  Not relevant to FocusFence, since ICAP is a server-side thing.  It does show that CloudVeil’s Windows filter could integrate external filters.  We can ignore ICAP for FocusFence’s local design.

- **e2guardian (C++, GPL‑2.0)** – A full web proxy/filter (forked from e2guardian project).  CloudVeil published it on GitHub.  *Relevance:* It’s a mature open-source content filter (like Squid + filters).  It demonstrates enterprise-grade URL/category filtering and text scanning.  However, it’s GPL-2 (viral) and very heavy C++ software.  It’s *too heavy* for Android and conflicts with CloudVeil’s GPL license.  For FocusFence, we should *not* adopt e2guardian code.  But it’s instructive about how category lists and regex/text triggers can be used (e.g. `forbidden site list`, phrase lists, etc.).  We treat it as a reference: FocusFence might offer some “default list” features inspired by these filters (e.g. hosts-based blocking, basic patterns) but not run a proxy like this.

- **AndroidChromium (Java, Apache‑2.0)** – A CloudVeil fork of Android’s Chromium browser, with built-in “on-demand URL and domain filter”.  It is a specialized browser client that enforces CloudVeil’s filtering inside the browser.  *Relevance:* This tells us CloudVeil’s approach on Android was to hard-code filtering into their browser.  For FocusFence, this is a cautionary note: shipping a custom browser is far beyond our scope.  Instead, we rely on a VPN/Accessibility solution.  Still, it underscores one idea: if you control the browser UI, you can enforce very granular rules (like blocking YouTube Shorts via UI).  But since we won’t have our own browser, we’ll likely mimic some of this with Accessibility (as discussed).  We won’t copy any Chromium code, but we should remember that fine-grained blocking (e.g. excluding *“/shorts”* paths) is possible if you control the browser.

- **filterproviderlib‑apple (Swift, MIT)** – (Covered above.)

- **FilterCore.Windows / CitadelCore.Windows (C#, MPL-2.0)** – These are platform-specific adapters for Windows (not Android).  *Relevance:* They illustrate how CloudVeil implemented traffic diversion on Windows (probably using WinDivert, etc.).  Not directly useful in Android, but reinforce that each platform needs its own network-hook logic.

- **NsfwNET / NsfwSqueezenet (C#, MPL‑2.0)** – Archived libraries/models for NSFW image classification.  *Relevance:* Show that CloudVeil experimented with local image recognition for adult content.  Not practical for FocusFence (heavy models, OpenCV, Windows-only native DLLs).  But it signals the idea of “local content classification” for images.  We likely won’t implement this in Android.  The fact these are archived and Windows‑focused suggests CloudVeil moved away from it.

- **WinDivert-related (WinDivertSharp, Divert)** – These are bindings/wrappers for the WinDivert packet capture driver.  *Relevance:* Unneeded for Android, since Android VPN is the analog.

- **Various Android/iOS/Telegram forks (CloudVeilMessenger, etc.)** – These are Telegram client forks with CloudVeil branding.  Per instructions, we treat them as irrelevant except that they show CloudVeil’s mobile dev efforts.  They aren’t filtering code.  (Note: Filter-Windows’ *Warden* had a “Telegram hook” on Windows, but that’s not in the public code.)

- **CloudVeil Blue, kitura, named-pipe, etc.** – Peripheral (branding, web frameworks, utilities).  Not relevant to filtering.

**Summary:** The most pertinent CloudVeil repos for FocusFence are the filtering engines (DistillNET, CitadelCore/FilterCore, e2guardian for ideas), the Windows filter suite (architectural lessons), and the Android filter attempts (AndroidChromium).  Many repos (Telegram clients, e-commerce monitoring, Swift frameworks) are not relevant.  Key themes are: *filter engine vs. platform adapter*, *list/categorized blocking*, *policy vs. UI separation*, and *practical constraints (performance, privacy)*.  

# Key Architectural Lessons

1. **Separate Engine vs Platform Integration.**  CloudVeil consistently decouples the core filtering logic from the OS integration.  For example, *CitadelCore/FilterCore* encapsulate HTTP(S) parsing and rule matching, while separate components (WinDivert, FilterAgent, tun2socks) handle traffic capture.  This suggests FocusFence should likewise have a modular design: a central **policy engine** (matching DNS/URL/rule lists) and pluggable enforcement layers (Android VPN, Accessibility hooks, etc.).  This avoids re-implementing parsing for each method of observation.

2. **Domain/URL Filtering as First Class.**  DistillNET and FilterCore show that efficient domain/URL matching (ABP rules, wildcard domains, hostlists) is a solved problem worth adopting.  FocusFence should lean on DNS/domain blocking and ABP-like path rules (e.g. block “youtube.com/shorts”) rather than invent new pattern syntax.  In practice, this means supporting existing filter list formats (EasyList, host files) and possibly ABP rules (as DistillNET does) so users can leverage community-curated lists.

3. **Category-based Policies (With Caution).**  CloudVeil’s manager can categorize sites (e.g. “adult,” “social”) and assign categories to groups.  While FocusFence is personal-use (not multi-user), this highlights that *tagging* sites or apps by category is useful.  We might allow users to enable/disable whole categories (like adult or social media) if we have good sources.  But unlike CloudVeil, FocusFence should avoid opaque or outsourced categorization (like zvelo) and give users control.  The CloudVeil approach suggests building in *some* category logic, but FocusFence might primarily let users pick lists/sources rather than managing a central DB.

4. **Local vs Remote Control.**  CloudVeil’s products are designed for parental/enterprise control with remote dashboards.  FocusFence’s philosophy is the opposite: the user is the owner and controller.  Everything learned from CloudVeil’s architecture that assumes a remote authority should be inverted.  For example, features like *InstallGuard* (prevent uninstall) or user reporting (Warden) are antithetical to FocusFence’s goals.  Instead, focus on *self-binding commitments* (like time locks) that the user opts into, rather than admin-forced blocks.  If an “admin” mode is supported (e.g. Device Owner tests), it should be optional and user-controlled.

5. **Light Touch on Content Inspection.**  CloudVeil includes heavy content inspection options (OpenNLP, HTTPS proxy/MITM).  These raise privacy and complexity issues.  For FocusFence’s local-first and privacy focus, we should prefer **shallow observation** (e.g. seeing domain names, SNI, or browser UI text via Accessibility) rather than deep packet inspection.  The distinction is clear: suspending an app (enforcement) doesn’t require knowing its URLs, but blocking “YouTube Shorts” requires either URL parsing or UI context.  CloudVeil did HTTP/S proxy MITM for deep filters (with ICAP and even HTTPS decryption), but FocusFence will likely avoid on-device TLS MITM unless absolutely necessary (and probably never – it’s invasive and breaks trust).  The lesson: heavy content scanning is powerful, but it's disallowed by our privacy criteria.

6. **Leverage DNS Filtering but Acknowledge Limits.**  FocusFence already uses DNS-based blocking (StevenBlack, etc.).  CloudVeil also recognizes DNS filters as one layer (their Filter-Windows likely supports hostlists).  However, both agree a blacklist is only as good as its data.  We should provide good default lists (ads, trackers, malware) from maintained sources, but not pretend they are complete.  CloudVeil’s practice of combining lists (like DistillNET with adult domains) suggests offering multiple list sources.  Yet CloudVeil also had fallback engines (text triggers, ML).  For FocusFence, we should acknowledge that DNS-only cannot catch all “distraction” content (e.g. YouTube vs YouTube Shorts requires more than domain), so we layer optional mechanisms (e.g. Accessibility).

7. **Battery and Performance Awareness.**  CloudVeil code does not appear to focus on mobile battery (it’s mostly desktop/server code).  This teaches FocusFence what *not* to do: avoid continuous polling, heavy wakeups, or frequent proxies.  The use of tun2socks and proxies suggests potential battery drain.  We should plan to benchmark any heavy approaches.  For example, Android’s VpnService must run as a long-lived foreground service; any DPI engine there would cost CPU and wakeups.  DistillNET’s cache idea (10-minute cache dramatically sped up lookups) hints at how to reduce work (e.g. DNS caching, batched rule matching).  In short, we must profile idle drain (CPU/timers) and prefer low-overhead techniques (simple domain blocklist in a VPN takes little power).

8. **Ease of Disable/Breach.**  CloudVeil’s product assumption is an admin who enforces compliance.  For FocusFence, we expect the user *may* want to disable (for dev work, QA, PCAPdroid).  So design commit/lock features as optional and reversible: e.g. a built‑in delay (StrictLock), or an admin PIN, not a forced admin disable.  Not much specific code here, but CloudVeil’s heavy-handed approaches (install guards, per-app prohibition) are **exactly what to avoid** for the owner’s tool.  We might still allow something like “lockout with timer” (as FocusFence already does with StrictLock.kt), but with escape hatches (safe mode, developer flag, etc.).

9. **Filter Data Sources and Updates.**  CloudVeil uses 3rd-party lists (they mentioned EasyList, zvelo, etc.) and their own category databases (likely proprietary).  We should gather what we can: StevenBlack hosts (already used), EasyList (ads), EasyPrivacy, etc.  One must note that CloudVeil likely has private ML/category data (not public).  In contrast, FocusFence should rely only on open lists or let users supply them.  The “filter source” abstraction is wise: FocusFence can allow enabling/disabling multiple feeds.  But CloudVeil’s lesson is that big engines are only as good as data; so we should prioritize well-maintained lists and not promise categories we can’t deliver reliably.  For example, CloudVeil’s adult filter likely uses both DNS and possibly images/text.  We might limit FocusFence to known text-based lists.

10. **Proven FOSS Practices.**  CloudVeil has released many components under open licenses (MPL, MIT, BSD).  This shows a willingness to open-core their tech.  We should carefully navigate licenses: most filtering code we admire from CloudVeil is MPL-2.0 (DistillNET, FilterCore), which requires preserving MPL notices and sharing modifications.  If FocusFence reuses or embeds any MPL-2 code, it must be MPL-2 licensed.  Any GPL code (e2guardian) is out.  If we want Apache/MIT licensing, we would have to reimplement functionality rather than copy MPL code.  (See *Licensing Issues* below.)  

# Components to Reuse or Study

- **List Management/Parsing:**  Reuse or reimplement the idea of ABP/domains filtering as in DistillNET.  We can’t drop C# code into Android, but the *algorithms* (inverted index by domain, caching) are worth porting or adopting from other open code (e.g. existing Java/Android ABP libraries like the one in Adblock-Plus).  If a suitable Java ABP engine exists (e.g. *Adblock Plus Engine for Android*), that might be leveraged under a compatible license.  If not, a custom Kotlin engine inspired by DistillNET’s approach could be written.  *FocusFence should have a robust rule matcher, not just linear search of lists.*  

- **Datastore Format:**  CloudVeil often uses SQLite or in-memory DB for rules (DistillNET uses its own DB).  We should pick a format optimized for lookups (perhaps a SQLite table indexed by domain, or an in-memory trie).  We should study CloudVeil’s notion of “multiple inserts for multi-domain rules”.  A practical approach: use a SQLite database with `domain` and `rule` columns, or even a compressed in-memory trie (e.g. [AndroidDNS's radix tree](https://github.com/YukiZero/AndroidDNS)).  Bloom filters (CloudVeil once considered) could accelerate existence checks for huge lists, but must be sized carefully.  FocusFence might not need millions of domains yet – realistic target may be ~100k–1M domains.  Modern devices can handle that in a trie (few MBs) or SQL index.  If users add custom lists frequently, dynamic updates matter.  So: study how DistillNET compiles rules (its benchmarks show millions of filters parsed quickly) and design data loading to be done offline (e.g. at boot or on demand).

- **Policy Engine Abstraction:**  CloudVeil has a complex policy (groups, exceptions, schedules).  For FocusFence, a simplified policy engine is needed: e.g. “if app=X or URL category=adult and schedule=2–5pm, then block”.  We should consider separating *conditions* (time, weekday, remaining budget) from *rules* (what to block) similar to a firewall policy.  It may not require a full-rule engine (like a firewall with if-then), but a structured configuration format helps.  Look at how CloudVeil likely stores policies (filter lists by category, plus exceptions).  We might not reuse code, but we should allow configs like: **Allowlist*, *Blocklist*, *Whitelist exceptions*, *Schedules*, *Per-app overrides*.  The repository FilterManager hints that policies had groups and category assignments; a scaled-down local version could exist (e.g. all blocked content is “Strict”, everything else “Default”).

- **Data Sources (“Filter Sources”):**  CloudVeil lumps domain lists (ads, adult, malware) and possibly textual triggers.  FocusFence should similarly be able to import multiple independent sources.  Instead of hardcoding StevenBlack only, allow users to specify or enable known feeds (e.g. EasyList, EasyPrivacy, malwaredomains, AdultSites, etc.).  We must research open lists (see FOSS research pass).  We should probably allow enabling/disabling by category and show provenance.  CloudVeil used category-labeled lists (e.g. adult_domains.txt).  For FocusFence, better to have *source lists with metadata* rather than just one big list.  For example, allow “ADS”, “MALWARE”, “SOCIAL” lists.  Combining them might cause duplicates, but that’s okay if internal index is robust.  The filter engine should tag each block hit with the list source (for local stats).

- **Performance Techniques:**  DistillNET’s emphasis on caching suggests that if we do heavy matching (especially in a VPN service), we should cache positive/negative matches per domain for some time.  Also, doing work only on DNS or on outgoing connection lookup to domain name (if HTTPS DNS isn't used) is best.  We should measure DNS lookup times, and maybe use Android’s Private DNS APIs or VpnService intercept.  If optional full VPN is used, packet-level inspection should minimize work (maybe only reading IP dst, lookup domain from an internal DNS stub, etc.).  In short: emulate DistillNET’s strategy of trading memory for speed, but with conscious limits for mobile.

- **Local Storage & Updates:**  CloudVeil probably updates lists on a schedule.  FocusFence can similarly download updates for StevenBlack/EasyList/etc. (with user permission).  Alternatively, use Play’s Schedules or WorkManager.  It’s likely fine.  No obvious CloudVeil code here, but keep in mind to do this off-main-thread and not too frequently (battery).

# Projects to Study (But Avoid Adopting Directly)

- **Adguard’s Filtering Engine / uBlock Origin:**  Although not CloudVeil projects, these FOSS engines (written in JS/C++) are mature and often cited by ad-blockers.  They are client-side and optimized (uBO’s C code in Brave, AdGuard’s filters).  Studying their rule formats (e.g. advanced ABP syntax, exception handling) and implementation patterns can inform FocusFence.  We will likely rely on simplified ABP subset.  CloudVeil’s DistillNET already covers ABP basics.  We should examine if a lightweight ABP engine for Android already exists (e.g. Adguard Android’s core is not open, but other libraries like [adblock-android by gorhill](https://github.com/gorhill/adblock-android) are available under GPL/MIT).

- **NetGuard (Android VPN Firewall)** – A popular FOSS Android app (GPL) that uses Android VPN to block per-app network.  It’s a potential alternate approach to VPN-based blocking.  It may use iptables or toggling VPN routing.  Studying NetGuard could reveal how to minimize battery usage with VpnService, as it’s optimized for this.  However, NetGuard is GPL, so we wouldn’t copy its code into an Apache/MIT project.  But as an app, it shows what’s possible on unrooted Android.  We should note if NetGuard’s user experience or techniques (e.g. turning off VPN quickly) can be applied.

- **DNS66 / PersonalDNSFilter / RethinkDNS (Android DNS blockers)** – These use the Android VpnService in DNS-only mode (socks5/dns proxy) to block domains.  They are similar in spirit to FocusFence’s DNS approach.  They handle domain lists and might have efficient list storage (some use SQLite, some use suffix trees).  Review their architecture and performance.  On licensing: DNS66 is GPL-3, RethinkDNS is AGPL/MPL possibly.  We should glean how they manage lists (Database vs in-memory).  We won’t copy GPL code, but we can learn e.g. “DNS66 uses a TUN that captures only DNS queries, so it blocks at DNS layer only – this saves battery.”  

- **AdAway (Android hosts-file adblock, GPL)** – Follows a hosts file approach (DNS64 technique on VPN).  Not exactly what we want (since it rewrites /etc/hosts), but conceptually similar to domain blocking.  Its approach of updating lists and using the VpnService is worth noting.  

- **AdGuard Home / Pi-hole (DNS server)** – Standalone DNS servers for adblocking.  We won’t embed a DNS server, but their data sources (and whitelisting approach) are relevant.  They show how combining lists works (e.g. default blocklist plus category lists).  Also note “adguard supports custom rules and exception domains.”  Might influence FocusFence design: e.g. allow per-app exceptions by re-running patterns.

- **Polipo/Privoxy (lightweight proxies)** – Traditional HTTP proxies that did filtering (Privoxy has action files).  For historical interest, to see lightweight rule engines.  Probably not directly relevant.

- **Categorization Feeds:**  Not a project, but CloudVeil mentioned external category services (like zvelo).  We should research what open lists exist: e.g. [PhishingArmageddon’s phishing list](https://github.com/mitchellkrogza/Phishing.Database), Spamhaus adult lists, etc.  Also lists like #SafeSearch (Google, Bing) may exist via DNS or VPN flags (DNS66 toggles them).  The research should enumerate feeds (see FOSS pass).

# Components Largely Irrelevant to FocusFence

- **Remote Management (FilterManager, CitadelManager)** – Entire UI backend.  FocusFence explicitly rejects remote dashboards or accounts.

- **HTTPS MITM and ICAP (CitadelCore, dotnet-icap, e2guardian)** – FocusFence is unlikely to intercept HTTPS content.  These are beyond our scope and against privacy principles.

- **User Monitoring/Reporting (Filter-Windows Warden, FilterManager reports)** – Any surveillance or logs for a third party should be avoided (FocusFence is user-centric).  Local stats are fine, but nothing to upload.

- **Obscuring Traffic (WinDivertSharp, Divert)** – Windows-specific hooking has no place on Android.

- **Image/Video ML (NsfwNET, image triggers)** – Machine learning for content (image NSFW, NLP) is tantalizing but not practical for on-device, low-power usage.  FocusFence should stick to simpler signals unless a developer explicitly wants to integrate TensorFlow Lite models; even then, likely not at launch.

- **Custom Browser (AndroidChromium)** – Developing or requiring a special browser is out of focus. FocusFence should integrate with whatever user uses (Chrome, Firefox, etc.), primarily via VPN or Accessibility.

- **Proprietary Category Databases (zvelo, CloudVeil DBs)** – Any closed-source or paid DBs CloudVeil uses can’t be copied.  We must rely on public lists only.

- **Enterprise/Parental Policies (DCM, Knox, device-owner lockdown)** – CloudVeil’s Windows/Mac filters often relied on admin privileges.  FocusFence should not try to replicate MDM features.  Device Owner mode might be an *option* for experiments, but not the default.

# Licensing Considerations

The choice of FocusFence’s license will crucially affect reusability of CloudVeil code and other open components:

- **GPLv3/AGPL:** Strong copyleft – any derivative work must be GPL-licensed, which might deter contributions and is not needed for a personal tool.  GPL would *prohibit* including any code under incompatible licenses (e.g. Apache 2.0 without relicensing).  It would also conflict with DistillNET’s MPL-2.0 (MPL-2 is not GPL-compatible by default).  AGPL is even more restrictive (network service distribution triggers).  Unless FocusFence wants to be a community project with share-alike, GPL is likely too heavy.

- **MPL-2.0:** A “file-level” copyleft (we must share changes to MPL-licensed files, but can combine with other code).  This is the license of most CloudVeil filtering code (DistillNET, FilterCore, etc.).  If FocusFence itself were MPL-2.0, it could legally include and modify that code, while allowing linking to other licenses (Apache, MIT) in separate files.  MPL permits mixing with proprietary code under conditions; it’s more permissive than GPL on combined works.  Choosing MPL-2.0 would align with CloudVeil’s open filter libraries, making reuse simpler.  However, MPL is less common in mobile apps, so consider community expectations.

- **Apache-2.0 / MIT:** Permissive – minimal obligations (only attribution and patent grant for Apache).  Easy for adoption and contributions.  However, these licenses are *incompatible* with MPL-2.0 when it comes to relicensing: you cannot simply take MPL code (e.g. DistillNET) and relicense it as Apache/MIT.  At best, you could link to a DistillNET binary or separate library, but in an Android app that’s messy.  In practice, with Apache/MIT, one would need to *reimplement from scratch* any MPL-2.0 code.  So if we want an Apache/MIT project, we cannot directly reuse DistillNET/FilterCore code (and similarly cannot use e2guardian’s GPL code).  That means either dropping those components entirely or rewriting them ourselves.  

- **Proprietary or other FOSS licenses:** Clearly not intended; FocusFence should remain fully FOSS for trust and modifiability.

In summary: **MPL-2.0** is the safest license *if* we plan to incorporate or fork any CloudVeil filtering libraries.  **Apache-2.0** or **MIT** (common for Android) are easier for contributors, but would force us to reinvent DistillNET-like functionality independently.  If we adopt Apache/MIT, we should confirm we can meet our needs with alternative libraries or new code.  In either case, we must avoid GPL-licensed components (e2guardian, NetGuard’s GPL parts, etc.).

# Conclusion

The CloudVeil repositories reveal a mature, multi-layer filtering architecture built for parental controls.  FocusFence’s goal is more modest: a *personal, no-remote-admin* toolkit.  We should borrow CloudVeil’s filter-engine ideas (fast ABP matching, DNS lists, policy abstraction) but reject its heavy enterprise features (remote management, invasive inspection).  The most valuable takeaways are modular design, leveraging existing blocklists, and careful balancing of enforcement vs. observation.  Technical reusability of their code is limited by platform (C# vs Android) and licenses (MPL vs Apache/MIT).  Architecturally, we must aim for a clean, lightweight engine with optional enforcement layers (VPN, Accessibility) while preserving privacy.  The result will be a new design informed by CloudVeil’s lessons, not a clone of its implementation.
